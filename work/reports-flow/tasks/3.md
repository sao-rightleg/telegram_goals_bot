# Task 3: Report SQLite Repository

## Required Skills

Before executing the task, load:
- `/skill:code-writing` - [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Add technical SQLite state for report job runs and delivery idempotency without creating business-primary tables. This allows reruns to skip successful recipient/report sends while preserving Google Sheets as the final business data source.

## What to do

- Add `report_job_runs` and `report_delivery_log` technical tables through the SQLite schema bootstrap.
- Add a report repository for job run lifecycle and delivery log idempotency operations.
- Keep table names out of `BUSINESS_PRIMARY_TABLES`.
- Enforce recipient-level unique delivery identity from the tech-spec.
- Do not store final report business content in SQLite.

## TDD Anchor

Tests to write BEFORE implementation. Write -> run -> confirm they fail -> write code -> confirm they pass.

- `tests/test_sqlite_schema.py::test_report_tables_are_technical_not_business_primary` - report technical tables exist and `report_runs` is not created.
- `tests/test_reports_repository.py::test_report_job_run_records_lifecycle_status` - repository starts and finishes a report job run.
- `tests/test_reports_repository.py::test_report_job_run_idempotency_key_is_unique` - duplicate job key is handled deterministically.
- `tests/test_reports_repository.py::test_delivery_log_prevents_duplicate_successful_send` - successful recipient/report item can be detected before resend.
- `tests/test_reports_repository.py::test_delivery_log_records_failure_and_attempt_count` - failed deliveries record sanitized error and attempts.

## Acceptance Criteria

- [ ] SQLite creates `report_job_runs` with the fields and checks from tech-spec.
- [ ] SQLite creates `report_delivery_log` with the fields, checks, and unique key from tech-spec.

- [ ] Repository supports start/finish job run operations.
