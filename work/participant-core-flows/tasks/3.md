# Task 3: SQLite dialog state repository

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Add a small repository for current dialog/menu technical state using the existing `dialog_states` table. This supports consent/menu flow persistence without creating business storage in SQLite.

## What to do

- Add a repository for upserting, reading, and clearing dialog state by Telegram ID.
- Use only the existing `dialog_states` table.
- Store technical flow values for consent, idle, and read-only views.
- Keep repository inputs explicit and avoid storing goal/step/report business facts.
- Use temporary SQLite databases in tests.

## TDD Anchor

Tests to write BEFORE implementation. Write → run → confirm they fail → write code → confirm they pass.

- `tests/test_dialog_state_repository.py::test_upsert_and_get_dialog_state` — repository stores current technical state.
- `tests/test_dialog_state_repository.py::test_upsert_replaces_state_for_same_telegram_id` — Telegram ID remains unique.
- `tests/test_dialog_state_repository.py::test_clear_dialog_state_removes_row` — state can be cleared.
- `tests/test_dialog_state_repository.py::test_repository_uses_existing_schema_only` — no business tables are created by the repository.
- `tests/test_dialog_state_repository.py::test_invalid_flow_fails_clearly` — unsupported flow values are rejected by repository or SQLite constraint.
