# Task 3: SQLite technical-state schema

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Implement SQLite schema initialization for technical state only. The result must support dialog/draft/scheduler/reminder/error state and must not create business-primary storage. Treat `docs/05_sqlite_state_schema.md` as the logical source of truth and complete it into an explicit physical SQLite schema.

## What to do

- Implement SQLite schema initialization using the standard library.
- Create only technical-state tables from the approved schema, including a `draft_sessions` owner table for `draft_id`.
- Add primary keys, unique constraints, indexes, and `CHECK` constraints for known technical enum values where practical.
- Add idempotency constraints for scheduler jobs, job runs, and reminder sends.
- Provide a small API to initialize and inspect schema state.
- Add tests proving business-primary tables are not created.

## TDD Anchor

Tests to write BEFORE implementation. Write → run → confirm they fail → write code → confirm they pass.

- `tests/test_sqlite_schema.py::test_init_creates_required_technical_tables` — all required technical tables exist.
- `tests/test_sqlite_schema.py::test_init_does_not_create_business_primary_tables` — participants/goals/weekly reports business tables are not created.
- `tests/test_sqlite_schema.py::test_init_is_idempotent` — running schema init twice succeeds.
- `tests/test_sqlite_schema.py::test_draft_sessions_owns_draft_id` — draft-related tables have a shared technical draft owner.
- `tests/test_sqlite_schema.py::test_scheduler_and_reminders_have_idempotency_constraints` — duplicate jobs/runs/reminders are prevented by schema constraints.
- `tests/test_sqlite_schema.py::test_schema_has_lookup_indexes` — scheduler, reminder, dialog, draft, and error lookup indexes exist.

## Acceptance Criteria

- [ ] SQLite schema initializer creates required technical-state tables.
- [ ] `draft_sessions` owns draft lifecycle and joins draft messages, attachments, reports, and insights.
- [ ] Primary keys, unique constraints, indexes, and practical `CHECK` constraints are present.
- [ ] Scheduler/reminder idempotency is enforced at schema level where possible.
- [ ] Schema initialization is idempotent.
- [ ] Business-primary storage tables are not introduced.
- [ ] Tests use temporary SQLite databases.

## Details

**Files:** `app/storage/sqlite.py` — schema initialization and inspection helpers.  
**Files:** `tests/test_sqlite_schema.py` — schema tests.

**Dependencies:** Task 1.

**Edge cases:** Empty database, repeated initialization, invalid parent path, duplicate reminder sends, duplicate job idempotency keys, draft rows without a draft owner, accidental creation of business tables.

**Implementation hints:** Keep SQLite limited to technical state from `docs/05_sqlite_state_schema.md`; do not add participant, team, goal, planned-step, weekly-report, insight, or final-report business-primary tables. It is acceptable to add technical helper tables such as `draft_sessions` when they make the approved logical schema coherent.
